# Tremor — Project Progress & Implementation Report

This document serves as an exhaustive, step-by-step progress and implementation summary for the **Tremor** project—a live, full-stack Wikipedia edit war seismograph and conflict mapping application. It details every architectural decision, codebase modification, user interface redesign, and performance optimization implemented throughout development.

---

## 1. PROJECT STATUS OVERVIEW
The **Tremor** application is fully implemented, running, and optimized. It ingests live Wikipedia revision streams, detects disputes and revert cycles via heuristic algorithms, calculates statistical rolling Z-score anomalies, clusters disputes using machine learning topic embeddings, maps them onto a 2D interactive coordinate grid, and provides plain-English summaries of disputes.

* **Backend Dev Server:** running on `http://127.0.0.1:8000` via Uvicorn (FastAPI)
* **Frontend Dev Server:** running on `http://localhost:3000` via Next.js
* **Database:** SQLite (`backend/dev.db`) populated with 1,160+ live-ingested pages, historical revision logs for contested pages, and coordinates computed via UMAP and HDBSCAN.

## 2. DETAILED ARCHITECTURAL BREAKDOWN

### A. Ingestion Pipeline
The application runs a dual ingestion pipeline:
1. **Real-Time Stream Listener (`backend/app/ingest/stream_listener.py`):**
   * Listens to the Wikimedia EventStreams Server-Sent Events (SSE) endpoint (`https://stream.wikimedia.org/v2/stream/recentchange`).
   * Filters incoming stream data for English Wikipedia (`wiki == "enwiki"`) and main namespace (`namespace == 0`).
   * Extracts essential metadata: page title, edit timestamp, editor username, edit comment, bot status, and revision byte difference.
   * Handles Windows console Unicode printing crashes. If the terminal encoding is unable to display specific characters, the backend sanitizes the output and logs it as clean ASCII to prevent process termination.
   * Stores revisions into the SQLite database dynamically.
2. **Historical Backfiller (`backend/app/ingest/history_fetcher.py`):**
   * Connects directly to the official MediaWiki Action API (`/w/api.php`).
   * Uses customizable headers (including proper `User-Agent` declarations) to prevent Wikipedia from returning HTTP 403 blocks.
   * Fetches up to 100-500 historical revisions for targeted high-conflict articles (e.g., *Barack Obama*, *Donald Trump*, *Israel*, *Gaza Strip*) to construct baseline activity profiles.
   * Automatically calculates byte diffs between sequential historical revisions.
   * Scans and flags historical bots and reverts using heuristic identifiers.

### B. Heuristics & Machine Learning Pipeline
1. **Revert Detection (`backend/app/ml/revert_detect.py`):**
   * Classifies edits as reverts if edit comments contain patterns like `revert`, `undid`, `rv `, `rvv`, `restored`, `undo`, or if Wikipedia's metadata tags indicate a rollback.
2. **Anomaly Scoring (`backend/app/ml/anomaly.py`):**
   * Calculates conflict intensity for each page hourly: `intensity = base_weight + (5.0 * is_revert)`.
   * Standardizes user edits with a weight of `1.0`, while bot edits are downweighted to `0.1` to ignore automated formatting noise.
   * Computes a rolling Z-score over the **last 24 hours** relative to the page's historical baseline.
   * Includes bonus multipliers based on the number of unique editors and revert frequency in the current active window.
   * Enforces a minimum revision count of `5` to prevent new pages with only 1 or 2 edits from spiking to abnormal conflict scores.
3. **Sentence Embeddings (`backend/app/ml/embeddings.py`):**
   * Extracts page summaries and recent edit comments, generating dense semantic embeddings using HuggingFace's `all-MiniLM-L6-v2` transformer model (384 dimensions).
4. **Topic Projection & Clustering (`backend/app/ml/clustering.py`):**
   * Projects high-dimensional text embeddings into a visualizable 2D coordinate space (`x`, `y`) via **UMAP** (Uniform Manifold Approximation and Projection).
   * Identifies logical dispute boundaries using **HDBSCAN** (Hierarchical Density-Based Spatial Clustering of Applications with Noise), classifying pages into numeric clusters representing shared disputational subjects.
   * Automatically adjusts minimum cluster sizes to prevent errors if the dataset is small.
   * Exposes `/api/clusters/recalculate` to run UMAP + HDBSCAN in background threads.

### C. Smart Summarization Layer (`backend/app/llm/summarize.py`)
* Leverages Gemini or Groq SDKs to write brief, objective descriptions explaining what the dispute on the page is about.
* Includes a **robust rule-based heuristic fallback parser** which is invoked if LLM API keys (`GEMINI_API_KEY`, `GROQ_API_KEY`) are missing, expired, or rate-limited.
* The fallback parser calculates edit counts, revision sizes, active revert ratios, lists top editors, scans edit comments for keyword groups (e.g., "geopolitics", "election", "science", "biography"), and prints an structured summary outlining the scale, frequency, and keyword context of the dispute.

## 4. COMPREHENSIVE PERFORMANCE OPTIMIZATIONS

### A. React Rendering Strain & Keystroke Lag
* **The Problem:** When typing in the search bar or the filter inputs, the dashboard experienced a significant keystroke lag. This occurred because React was forced to re-render and perform DOM reconciliation for the entire list of 1,160+ items on every keystroke, while simultaneously recalculating coordinate projections for the SVG UMAP cluster graph and Recharts area charts.
* **The Solution:**
  1. **Result Slicing:** Modified the client-side search logic in `frontend/src/app/page.tsx`. The component now filters matches based on the query, but restricts the rendered output using `.slice(0, 80)`. This cuts out unnecessary DOM footprint and ensures list rendering is instantaneous.
  2. **Component Memoization:** Used `useMemo` hooks to isolate components from the dashboard's parent state updates. Now, typing in a text input *only* triggers recalculation of the text search query state, while the rest of the application remains untouched:
     * `umapSvg` is memoized and only recalculates when clusters or the active node selection change.
     * `timelineChart` is memoized and only recalculates when the detail state of the selected page changes.
     * `revisionLog` is memoized and does not refresh unless the list of recent revisions changes.
     * `adjustedNodes` memoizes a screen-space coordinate layout.
  3. **Node Collision Relaxation:** Added an inline screen-space collision relaxation algorithm in the UMAP `useMemo` block. It loops 15 times to push close-together points apart, ensuring nodes are clearly clickable and visually readable without overlapping.

### B. SQLite Concurrency (WAL Mode)
* **The Problem:** The ingestion pipeline (`stream_listener.py`) writes new events continuously, while the scoring algorithm (`anomaly.py`) reads/writes scores, and the FastAPI server reads the DB. This led to frequent database lock failures (`sqlite3.OperationalError: database is locked`), crashing page detail fetches on the frontend.
* **The Solution:**
  * Modified `backend/app/db.py` to enable **Write-Ahead Logging (WAL)**.
  * Executed SQLite pragmas on connection: `PRAGMA journal_mode=WAL;` and `PRAGMA synchronous=NORMAL;`.
  * Added a `timeout: 30` parameter in connection arguments (`connect_args = {"check_same_thread": False, "timeout": 30}`).
  * WAL allows multiple readers to access the database concurrently while a write transaction is in progress, eliminating database lock errors.

### C. CORS Mismatches & Same-Origin Proxying
* **The Problem:** Browsers restrict requests sent from `localhost:3000` to local IPv4/IPv6 loopback interfaces (`127.0.0.1:8000`), resulting in CORS blockages.
* **The Solution:**
  * Updated `frontend/next.config.ts` to implement Next.js rewrite rules. All `/api/:path*` traffic is proxied on the server side to `http://127.0.0.1:8000/api/:path*`.
  * Set `API_BASE = ""` in `page.tsx` to issue relative network requests, routing all backend calls through the Next.js same-origin domain.

### D. About Page Scroll Lock
* **The Problem:** The interactive About page was locked to the screen height and could not scroll down to show methodologies or metrics tables, because it inherited global layouts.
* **The Solution:**
  * Configured the main container in `frontend/src/app/about/page.tsx` as `h-screen overflow-y-auto`.
  * This allows the page's internal scroll container to scroll independently, bypassing the global `body { overflow: hidden }` rule in `globals.css`.

## 7. PHASE 3 — LATEST STABILIZATION & PERFORMANCE IMPROVEMENTS (JUNE 2026)
We successfully completed all Phase 3 tasks, focusing on scalability, correctness of score distribution, clean TypeScript compile checks, and eliminating database bottlenecks:

1. **On-Demand Wikipedia Search & Track:**
   * Upgraded the filter input to a debounced (200ms) input.
   * Created new FastAPI endpoints: `GET /api/pages/search` to check the DB (including prefix and partial matches) and `GET /api/pages/check-wikipedia` to validate page existence and resolve redirects.
   * Kicked off on-demand tracking via `POST /api/pages/track` for unknown pages and implemented polling in Next.js to auto-navigate to the new page when done.
   * Polished empty states with clear CTA instructions for adding pages.
2. **Performance Optimization / Database N+1 Query Elimination:**
   * Found that scanning 15,000+ pages individually in a Python list comprehension caused serious N+1 performance issues in both `app.ml.anomaly` and the stream listener scorer thread.
   * Rewrote the queries to use a single SQL aggregate statement: `GROUP BY Revision.page_id HAVING count(Revision.id) >= 5`.
   * This decreased database check time from **minutes** to **0.16 seconds**, fully preventing database lockups.
3. **Compare Mode & Seismograph Visuals:**
   * Allowed Shift+clicking cluster nodes to enter Compare Mode, opening an inline panel displaying conflict scores side-by-side.
   * Added SVG `<animate>` rings for nodes with scores > 2.0 to simulate active seismograph spikes.
4. **Compile-Clean & Fully Tested:**
   * Cleaned up state variables (`loadingTrack`, `wikiNotFound`, `compareTimeline`) to achieve **0 compiler warnings/errors** in `page.tsx`.
   * Ran automated E2E tests verifying the end-to-end Wikipedia fetch, redirect validation, and correct score calculation.

## 8. PHASE 4 — RELIABILITY, SCORING CORRECTION, & REDIS QUEUE SYSTEM (JUNE 2026)
We successfully completed all Phase 4 features and reliability audits:

1. **Scoring Correction & Formula Re-tuning:**
   * **Re-scoring Model**: Resolved a regression where pages with thin or quiet recent history were over-corrected to `0.00` by introducing a two-component score wrapper `max(base_score, spike_score)`. The base score uses revert rates, volume, and edit-comment entropy to guarantee historically-contested pages retain a non-zero representation (e.g., Barack Obama ≈ 3.11, Donald Trump ≈ 4.38).
   * **Removed Score Caps**: Extracted the hardcoded artificial score ceiling of `5.0`. High-intensity, active edit conflicts can now scale to reflect their true statistical anomalies (e.g., 2026 FIFA World Cup ≈ 7.81, 2026 Labour Party crisis ≈ 8.13).

2. **Ingestion Reliability & Robust Fail-Safe Transactions:**
   * **Race Conditions Solved**: Handled transaction conflicts in the real-time stream listener (`stream_listener.py`) and history fetcher (`history_fetcher.py`) by wrapping page queries and insertions in a `db.flush()` + `except` rollback block to prevent database integrity crashes.
   * **Partial-Failure Rollback**: Wrapped the backfiller batch insertions in a master transaction that rolls back fully on failure, preventing database corruption from partial HTTP/network dropouts.
   * **DB Timeout**: Increased SQLite `busy_timeout` in `db.py` to `10000ms` (10s) to handle write contention when the live stream, backfiller, and background workers write to the database concurrently.

3. **Redis & RQ Worker Queue Integration:**
   * **Lazy Connection Setup**: Created `app/queue.py` utilizing a thread-safe double-checked lock pattern. Redis is connected lazily on the first request rather than at backend startup, avoiding blocking uvicorn imports.
   * **Graceful Degradation**: If Redis is unreachable, the system automatically runs the worker task inline inside FastAPI's `BackgroundTasks`, disabling response caching without throwing errors.
   * **Asynchronous RQ Job Worker**: Created `app/workers/track_worker.py` containing dedicated job functions. If Redis is available, the frontend receives a `job_id` and polls `/api/pages/track/status/{job_id}` displaying queue states (`queued`, `started`, `finished`).
   * **Response Caching**: Enabled a 30-second Redis cache on `/api/pages` and `/api/clusters` requests for near-instantaneous page reloads.

4. **Swiss Ticker Overlay & Badge Alignment:**
   * **CSS Layout Fix**: Resolved visual overlaps where the scrolling ticker text slipped underneath the crimson `LIVE` badge. Rewrote the layout in `globals.css` using `flex-shrink: 0` for the badge container and `flex: 1; overflow: hidden;` for the scrolling text track.
   * **Suppressing Linters**: Added `# type: ignore` comments to the lazy imports of `redis` and `rq` in `queue.py` to fix Pyrefly missing-import diagnostics.

## 9. PHASE 5 — UMAP CENTERING, BATCH LOADING, & STABILIZATION (JUNE 2026)
We successfully completed all Phase 5 improvements, focusing on UMAP layout centering, optimized paginated batch loading, a 2,000-article cap, and statistical scoring corrections:

1. **Symmetric UMAP Viewport Mapping & Default Coordinates:**
   * **Centroid Recentering**: Normalized computed UMAP coordinates in `clustering.py` so that their centroid matches `(0, 0)` exactly, and scaled coordinates to lie within the `[-1.0, 1.0]` bounds.
   * **Coordinate Defaults**: Set default values (`x=0.0`, `y=0.0`, `cluster_id=-1`) in `models.py` for new page records so that untracked pages render in the middle of the SVG rather than remaining invisible.
   * **Symmetric SVG Scaling**: Replaced the asymmetrical scaling logic in `page.tsx` with a scale factor computed using maximum absolute bounds (`maxAbsX`, `maxAbsY`), positioning coordinates symmetrically around the center.

2. **Dynamic Paginated Loading & Instant Feed Progression:**
   * **Initial Load Limit**: Configured the sidebar list to initially fetch and render only the top **300** tracked pages.
   * **Instant Paging Forward**: Programmed the "Load 100 More" action button to page forward through already-tracked articles in the DB/cache. If `renderedCount < totalTracked`, clicking the button increments the limit and reads from the database/Redis cache instantly without triggering a new Wikipedia fetch.
   * **Wikipedia Fetch Fallback**: When the rendered count is equal to the total tracked count and the cap isn't hit, the button falls back to querying the `POST /api/pages/load-more` endpoint to fetch and ingest 100 new pages from Wikipedia.
   * **Pattern-Based Cache Invalidation**: Modified `invalidate_page_caches()` in `queue.py` to dynamically query and clear all keys matching `tremor:pages_list:*` and `tremor:clusters_list:*` in Redis, supporting arbitrary paginated limits.

3. **Z-Score Anomaly & Numerical Stability Fixes:**
   * **Baseline Standard Deviation Floor**: Set a minimum floor of `1.0` on the baseline standard deviation `std_baseline` to prevent Z-score explosions when baseline activity is sparse.
   * **Trailing Silent Hours Padding**: Appended a zero-intensity dummy row at the current time `now` before resampling the time series. This ensures hours of silence between the last edit and the current moment are included in the recent 24h window mean, resolving score inflation bugs on quiet pages.
   * *Result*: Corrected the score for "Australian Institute of Architects Awards and Prizes" from `63.49` (High Conflict) to `0.89` (Quiet), matching its actual history.

4. **Database Cleanup & Cap Enforcement:**
   * **Cap Eviction (2,000)**: Enforced a strict 2,000-page limit in `track_worker.py` and `pages.py`. When the database exceeds 2,000, it automatically evicts the lowest-conflict, stalest articles, while protecting high-conflict pages (anomaly score > 2.0).
   * **Database Pruning**: Cleared over 33,000 redundant pages created by the background stream listener, pruning the database to a clean starting count of ~1,000 pages so that the cap logic functions properly and UMAP calculations run in seconds.
   * **Serial Numbers**: Added sequential numbering (`idx + 1.`) before each article title in the sidebar list to make the total visible count immediately obvious.
